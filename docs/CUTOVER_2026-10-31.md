# Car Doc Final Cutover — October 31, 2026

This runbook is for the Windows/Shopman32 → PlumWorks production cutover after business close on **Saturday, October 31, 2026**. Windows remains authoritative through October 31. PlumWorks becomes authoritative on **Sunday, November 1, 2026**.

## Non-negotiable gates

Do not proceed with destructive cutover unless every gate below passes.

1. UAT is approved and the production application/schema version intended for go-live is frozen.
2. No production data mutation is performed as part of readiness work before the approved cutover window.
3. The final Windows data snapshot is taken only after the owner stops entering October 31 activity.
4. Snapshot intake/manifest validation passes and the final source fingerprint is recorded.
5. Customer recovery approval is current and bound to the final snapshot when recovery is required.
6. Active Repair Order adjudication/resolution artifacts are current and bound to the same final snapshot when required.
7. The cutover dry-run/preflight reports zero blocking issues.
8. The preserved-state capture passes, including **zero marketing leads linked to customers that would be reset**.
9. The production public-schema backup completes and verifies before operational reset.
10. Authorization/signature evidence tables are empty or explicitly dispositioned. The cutover engine fails closed when evidence exists.
11. Post-load row-count, mileage, vendor, complimentary-labor, payment, AR, RLS and accounting checks pass.
12. The preserved-state post-cutover verification passes.
13. **October 2026 Sales Report parity passes to the penny.**
14. **2026 YTD through October 31 Sales Report parity passes to the penny.**
15. On November 1, the owner compares the final Windows October/YTD reports with the PlumWorks reports before normal operations begin.

A failure in any gate is a **NO-GO**. Keep Windows authoritative and use the verified backup/recovery plan rather than accepting a known mismatch.

## What the cutover already protects

The existing cutover engine validates required DBF/FPT sources, immutable source fingerprints, customer recovery, historical vehicle linkage, final open Repair Orders, payments/AR, mileage, vendor/source values, complimentary labor classification, database row counts, RLS protection, backup integrity, and lifecycle rules. It also blocks reset if migration-managed authorization/signature evidence exists.

Legacy customers are imported with `acquisitionSource = LEGACY`. Vehicle odometer and historical invoice odometer are imported and covered by cutover acceptance checks.

## New preserved-state gate

The existing cutover's internal settings snapshot predates some newer Car Doc configuration. The final-cutover process therefore adds an independent read-only before/after snapshot around the cutover.

It protects current shop configuration, tax/labor/shop-supplies settings, audit configuration, lead-notification settings, invoice footer/warranty/authorization/certification text, Michigan facility/technician information, next RO number, memberships, staff invites, canned services, employees, vendors, marketing content, leads, lead notifications and read state.

It also **blocks before reset** when a marketing lead is linked to an operational customer, because deleting that customer would clear the lead's `customerId` relationship.

Capture immediately before the approved destructive cutover:

```bash
node --env-file=.env.local scripts/final-cutover-preserved-state.mjs capture \
  --file reports/cutover-2026-10-31-preserved-state.json
```

Required result: `Linked marketing leads: 0`.

After the reload and built-in cutover verification:

```bash
node --env-file=.env.local scripts/final-cutover-preserved-state.mjs verify \
  --file reports/cutover-2026-10-31-preserved-state.json
```

Required result: `Preserved-state verification: PASS`.

## New October 31 report-parity gate

`npm run legacy:cutover:final-report-parity -- --source <FINAL_SNAPSHOT_DIR>` compares the final Windows source directly with imported PlumWorks legacy invoices for these exact ranges:

- October month-end: `2026-10-01` through `2026-10-31` inclusive.
- 2026 YTD: `2026-01-01` through `2026-10-31` inclusive.

The comparison is exact for:

- invoice count
- parts
- labor
- subtotal
- shop supplies
- ordinary sales tax
- discounts/reductions
- legacy additional charges
- gross sales
- invoice paid total

Any one-cent difference exits non-zero and is a NO-GO.

## Final read-only preflight

Run the existing cutover in dry-run/preflight mode against the final snapshot. Include the exact recovery/adjudication/resolution artifacts required by that snapshot.

```bash
npm run legacy:cutover -- \
  --source <FINAL_SNAPSHOT_DIR> \
  --snapshot-manifest <FINAL_SNAPSHOT_MANIFEST> \
  --customer-recovery-manifest <FINAL_RECOVERY_APPROVAL_JSON> \
  --customer-recovery-proposal <FINAL_RECOVERY_PROPOSAL_JSON> \
  --payment-date-policy invoice-date-proxy \
  --cutover-mode final-production \
  --preflight --dry-run --report
```

Add `--final-cutover-adjudication ...` and/or `--final-cutover-active-ro-resolution ...` when the final snapshot requires those reviewed artifacts. Omit customer-recovery arguments only when the preflight proves recovery is not required.

Review the generated JSON/Markdown report. Required result: no critical issues and no projected count inconsistencies. The dry-run must report zero database writes.

Then capture the preserved state using the command above. If it reports linked marketing leads, stop and review those records before reset.

## Confirmed production cutover

Only after the preflight and preserved-state capture are approved:

```bash
npm run legacy:cutover -- \
  --source <FINAL_SNAPSHOT_DIR> \
  --snapshot-manifest <FINAL_SNAPSHOT_MANIFEST> \
  --customer-recovery-manifest <FINAL_RECOVERY_APPROVAL_JSON> \
  --customer-recovery-proposal <FINAL_RECOVERY_PROPOSAL_JSON> \
  --payment-date-policy invoice-date-proxy \
  --cutover-mode final-production \
  --confirm-final-production FINALIZE_WINDOWS_PRODUCTION_CUTOVER \
  --reset-operational-data --reload-legacy \
  --backup --verify --report \
  --confirm RESET_SHOP_OPERATIONAL_DATA
```

Add the same final adjudication/resolution flags used by the approved preflight. The confirmation values above match the current cutover code; `legacy:cutover --help` remains authoritative if code changes before October 31.

Do not continue if backup verification or any post-load cutover verification fails.

## Rollback / NO-GO rule

If the confirmed cutover fails after reset begins, do not improvise database edits. Preserve logs/reports, stop PlumWorks transaction entry, restore/recover using the verified pre-cutover backup as appropriate, and keep Windows as the authoritative system until the blocking issue is understood and a clean cutover can be rerun under the lifecycle rules.
